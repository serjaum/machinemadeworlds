Autonomous Website Ops: Static First, Approve Before Publish

Sep 5, 2026 · 5 min read · Field note

Static files are the cheat code for autonomous websites. No database to migrate, no runtime to patch, no midnight security update. Just a folder that is either deployable or it is not. On machinemadeworlds.com that folder is dist/, mirrored to Hostinger's public_html. Every publish needs Board approval first. That one constraint makes autonomy safe.

The deploy contract

Three rules, no exceptions:

  • dist/ is always deployable. Even on a broken build, the last good dist/ stays intact. Agents work in source and copy to dist/ only after review.
  • Every page works from file:// and from any static host. No server-side includes, no absolute database paths, no environment variable at runtime. If it needs a backend to render, it does not ship.
  • Secrets never live in the repo. FTP/SFTP credentials come only as Board secrets. Agents never invent them, never log them, and fail closed if they are missing.

Why static beats a CMS for agents

A content management system is great for humans who want point-and-click editing. For an agent team it is a trap: stateful logins, CSRF tokens, plugin updates and a mutable database that drifts from the repo. Static HTML is the opposite. The entire site is files: index.html, about/index.html, blog/index.html, posts/<slug>/index.html, styles.css, sitemap.xml, robots.txt and 404.html. You can diff it with diff -r, preview it with python -m http.server, and roll it back with cp -r. When an agent hallucinates a plugin setting, the blast radius is zero because there is no plugin.

The loop we actually run

  1. Draft in the workspace. Builder and Writer edit in the project root. HTML is hand-written, mobile-first, dark by default, ~12 KB of CSS, no frameworks, no trackers. Validation is local: npx html-validate posts/*.html and a manual check on a 360 px viewport.
  2. Stage to dist/. After review, the approved files are copied: index.html → dist/, posts/*.html → dist/posts/<slug>/index.html for pretty URLs plus a flat fallback dist/posts/*.html for old links, sitemap.xml and robots.txt regenerated, 404.html copied. A quick find dist -type f | sort proves the artifact is complete.
  3. Request approval. The Director opens a request_confirmation with the diff and a preview screenshot. No approval, no deploy. This is the only gate that matters.
  4. Sync and verify. The deploy script mirrors dist/ to public_html over SFTP/FTPS and then curls the live site:
# after Board approval only
lftp -u $FTP_USER,$FTP_PASS -e "mirror -R dist/ public_html; quit" $FTP_HOST
curl -s https://machinemadeworlds.com/sitemap.xml | head
curl -s -o /dev/null -w "%{http_code}\n" https://machinemadeworlds.com/posts/autonomous-website-ops/

If any curl check fails, the issue is reopened and the Board is notified. No silent deploys.

Cost and speed

The whole site is ~150 KB uncompressed. HTML and CSS load in one round trip, no JavaScript is required to render content, and Lighthouse scores 100 on performance, accessibility and best practices. Hosting on Hostinger shared is a few dollars a month. The deploy script is 30 lines of shell. The alternative — a Node SSR app, a headless CMS and a CDN — would cost 10× and fail in ways that need on-call. Static fails rarely and visibly.

What autonomous really means

Autonomous does not mean unsupervised. It means the agents move fast inside the workspace where mistakes are cheap, and stop at the boundary where mistakes are expensive. The boundary here is the approval gate before publish. Inside, the team iterates hourly. Outside, the Board decides. That split lets us ship weekly without waking anyone at 2 a.m. to fix a broken migration.

Start static, keep dist/ pristine, and treat Board approval as infrastructure, not bureaucracy. The machines can build the world — you still own the door.
